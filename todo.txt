read_url 与 synthesis 图片下载逻辑差异总结
===========================================

1. 代码入口不同
- read_url 的实际入口链路是 `synthesis/sft/api_tools.py -> synthesis/sft/tools.py:read_url()`。
- synthesis 这边更强的图片解析/恢复逻辑在 `synthesis/image_discovery.py`，核心入口是 `_resolve_image_asset()`。

2. read_url 当前的图片处理逻辑
- `read_url()` 先调用 `_probe_content_type(url)` 做分流。
- 如果 `content_type.startswith("image/")`，才会进入图片分支。
- 图片分支内部基本只有三步：
  1) `_download_binary(url)` 直接下载目标 URL；
  2) `_maybe_resize_downloaded_image(...)` 只做缩放，不做恢复；
  3) 把结果写入临时文件并返回 `local_path`。
- 如果 `_probe_content_type(url)` 判断成 `text/html`，就不会尝试按图片处理，而是直接走 `_read_document()` 文本阅读分支。

3. image_discovery 当前的图片处理逻辑
- `_resolve_image_asset()` 会先尝试直接下载 `image_url`。
- 如果 direct 下载失败，不会立刻放弃，而是继续用 `source_page_url` 做恢复。
- `_recover_candidate_image_urls()` 会从 source page HTML 中提取多个候选图片地址，例如 `og:image`、`twitter:image`、`display_url`、`image_url`。
- 对恢复出的每个候选 URL，都会继续尝试真实下载和图片校验，而不是只取第一个字符串候选。
- 如果恢复出多张可下载图片，会再走 `_select_best_recovered_asset()`，结合 query / title / snippet 让 LLM 选出最符合当前搜索目标的一张。
- 整个过程中还有更完整的 debug 输出，例如 `image-download-ok`、`image-resolve-success`、`image-asset-ready`、`image-recovery-selection`。

4. 两者最关键的能力差异
- read_url 是“单 URL 探测 + 单次下载”。
- image_discovery 是“直接下载失败后，再基于 source page 做恢复、下载多个候选、再按 query 选图”。
- 因此对于 Facebook lookaside / Instagram lookaside / 登录壳页 / 跳转页这类场景，read_url 现在明显更薄。

5. lookaside 场景下的具体影响
- 像 `lookaside.fbsbx.com/...` 这类 URL，返回体经常是 `text/html` 壳页，而不是真实图片字节流。
- 在当前 read_url 逻辑下，这类 URL 大概率会被 `_probe_content_type()` 判成 `text/html`，然后直接切到文本阅读逻辑。
- 但 image_discovery 之所以还能拿到图，是因为它并不只看这个壳 URL；它会继续利用 `source_page_url` 去恢复真实图片地址，再下载真正的图片。

6. 当前 read_url 为什么没法直接等价复用这套增强逻辑
- read_url 的工具输入现在只有 `url` 和 `goal`。
- 它没有 `source_page_url`，也没有搜索结果里的 `title/snippet/query` 上下文。
- 所以 image_discovery 里“从 source page 恢复多个候选，再按 query 做 LLM 选图”的逻辑，不能原样无损搬进 read_url。

7. 如果后续要增强 read_url，至少要解决的问题
- 当 URL 返回 HTML 壳页时，不能直接把它当普通文本页结束；需要判断它是不是图片跳板页。
- 需要决定 read_url 是否要支持从 HTML 中恢复候选图片 URL。
- 如果恢复出多张图，需要明确 read_url 是：
  - 只取第一张可用图；
  - 取最大图；
  - 还是像 image_discovery 一样结合 query/goal 再选一张。
- 如果要完全对齐 image_discovery，可能需要给 read_url 扩参数，至少补充 `source_page_url` 或者更强的上下文。

8. 当前结论
- read_url 当前逻辑没有错，但职责更窄，适合普通直链 URL。
- 相比之下，synthesis/image_discovery.py 现在已经具备更完整的“图片恢复 + 候选筛选”能力。
- 因此，如果目标是让 read_url 也稳定处理 lookaside / 壳页型图片 URL，就需要把它从“单 URL 下载器”升级成“带恢复能力的图片解析器”。
